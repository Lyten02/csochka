# Правила работы с csochka

## Общение и ответственность

- Отвечать на русском. Пользователь ставит задачи в T3; основной ассистент выступает менеджером: уточняет результат, передаёт задачу оркестратору, следит за выполнением и возвращает проверенный результат.
- Для разработки использовать **Orca + OMP**. Orca показывает проект, рабочие каталоги и сессии; OMP управляет моделями и подагентами. Перед управлением Orca читать навыки `orca-cli` и `orchestration` через установленный CLI.
- Не заменять этот маршрут невидимыми T3/native подагентами без указания пользователя. Модель текущего чата не меняется от этих инструкций: Opus запускается отдельной OMP-сессией в Orca.

## Модели — требование владельца от 13.10.2026

- Оркестратор: **Claude Opus 5.5**, точный селектор OMP `anthropic/claude-opus-5-5`, по умолчанию `high`.
- Подагенты: **Astra / Sol**, селекторы `openai-codex/gpt-6-astra` и `openai-codex/gpt-6-sol`. Astra — сложная логика и независимая проверка; Sol — ограниченные задачи реализации.
- Минимальный уровень размышления **Medium**. Указывать его явно; для трудных задач допустимы `high`, `xhigh`, `max`. `off`, `minimal`, `low`, `auto` не использовать.
- Не подменять модели по ошибке доступа или лимиту. Сначала проверить каталог и ошибку; сообщить о неподтверждённой доступности. Prewalk отключён у оркестратора и исполнителей.
- Проектные настройки: `.omp/config.yml`; профили исполнителей: `.omp/agents/csochka-astra.md` и `.omp/agents/csochka-sol.md`. Запуск из корня: `pwsh -NoProfile -File tools/start-omp.ps1 -Role orchestrator` (либо `astra` / `sol`). Скрипт передаёт конфигурацию явным overlay, не меняя глобальные настройки.
- В OMP делегировать через `task` профилям `csochka-astra` / `csochka-sol`; их reasoning задан как `medium`. Не использовать другие обнаруженные профили. Для повышения reasoning отдельного исполнителя запускать его через скрипт с `-Thinking high` (или выше) в Orca.

## Цикл выполнения

1. Менеджер проверяет текущие Orca-сессии и Git-состояние. Повторно использует живой оркестратор этого проекта; после перезапуска заново получает handle через `orca terminal list`. Не дублирует уже выполняемую задачу.
2. Передаёт Opus самостоятельное задание: цель, файлы в области работы, ограничения, владение файлами, критерии приёмки и ожидаемые доказательства.
3. Opus декомпозирует работу и делегирует исполнителям Astra/Sol. Сам контролирует зависимости и проверяет результаты. Простые операции запуска/статуса менеджер может выполнять непосредственно.
4. Один файл/ресурс — один писатель. Независимые изменения при необходимости выполнять в отдельных Orca-worktree; чтение можно параллелить. Не запускать импорт Godot одновременно с изменением тех же ресурсов.
5. Для контролируемой работы использовать Orca Run/Task/Dispatch и завершение `worker_done` по живому preamble. При необходимости точных аргументов OMP сначала создать терминал командой запуска, затем привязать его через `worker-start --terminal`. Не считать `accepted: true` доказательством начавшегося или завершённого задания.
6. Перед закрытием задачи проверить отчёт исполнителя, фактический diff и подходящие проверки. После завершения явно сохранить оркестратор для следующих задач, а ненужных исполнителей освободить по протоколу Orca. Не создавать расписания без запроса.

## Репозиторий и проверка

- Сначала читать `README.md` и актуальные инструкции в области изменения; не переносить вслепую конфигурации других агентов.
- Игровой проект находится в `godot/`, Three.js-просмотрщик — в `web/`. Не менять оба варианта без необходимости.
- Проверять изменения соразмерно: для GDScript — импорт/проверка Godot и соответствующие тесты из `godot/tests`; для поведения — реальный запуск. Конфигурацию оркестрации проверять живым заданием с отчётами моделей. Не выдавать успешный старт за полноценный игровой тест.
- Сохранять чужие изменения. Не закрывать игру и приложения пользователя без разрешения. Не коммитить `.godot`, сессии, историю, credentials, токены, telemetry и runtime-отчёты с приватными данными. Локальные сведения об оркестрации хранить в игнорируемой `.orchestration/`.
- После завершённого изменения: проверки → commit → push → создать/обновить PR в `main`, вернуть ссылку. Указание «только локально» / «без push/PR» имеет приоритет. При отсутствии write-доступа использовать fork, сохранив `origin`.
- **Merge и auto-merge не разрешены** без отдельного явного запроса. Не обходить проверки. В описании PR держать актуальную цель, проверку, ограничения и доказательства; для визуальных изменений — 1–2 проверенных скриншота по устойчивым ссылкам.

## Подключение в Orca

Проект регистрируется по текущему абсолютному пути через `orca repo add --path <root> --json`. Существующий checkout использовать через `path:<root>`; runtime handle не фиксировать в Git.

Пример создания оркестратора из корня проекта (PowerShell):

```powershell
orca terminal create --worktree "path:$PWD" --title "csochka | Opus 5.5" --command 'pwsh -NoProfile -File tools/start-omp.ps1 -Role orchestrator' --json
```

Перед отправкой задания проверить `terminal read` и `terminal wait --for tui-idle`. Живые инструкции установленного Orca имеют приоритет над устаревшими примерами команд.
